# Traduction (i18n) — Lingo.dev

## Ce qui est en place

- `i18n.json` à la racine : source `en`, cible `fr`, bucket `json` sur `lang/[locale].json`
- `lang/en.json` : catalogue source (143 chaînes extraites des appels `__()` du code)
- `lang/fr.json` : traduction générée
- `i18n.lock` : empreintes des sources/traductions, **à committer** avec les fichiers de langue

Commande (depuis la racine) :

```bash
OPENAI_API_KEY=dummy bunx lingo.dev@0.138.10 i18n --no-interactive
```

Elle traduit uniquement les clés nouvelles ou modifiées, conserve les retouches manuelles de `lang/fr.json` et retire les clés supprimées de la source.

## Fournisseur IA : proxy local

`i18n.json` déclare un provider « BYOK » compatible OpenAI :

```json
"provider": {
  "id": "openai",
  "model": "opencode-go/deepseek-v4.1-flash",
  "prompt": "...",
  "baseUrl": "http://localhost:10100/v1"
}
```

- Le proxy tourne sur `http://localhost:10100` (auth locale) et expose `/v1/chat/completions`.
- `OPENAI_API_KEY` doit être défini mais n'est pas vérifié par le proxy : n'importe quelle valeur non vide suffit (`dummy`).
- Le prompt est le system prompt envoyé au modèle ; il doit rappeler de garder les clés JSON, les placeholders `:attribute` / `:count` et le HTML intacts.

## Deux CLI, une seule utilisable ici

| CLI | Version | Fonctionnement | Utilisable avec le proxy ? |
| --- | --- | --- | --- |
| `@lingo.dev/cli` (`lingo`, installé global) | 1.18+ | `push`/`pull` vers un moteur hébergé chez Lingo.dev (org + engine + `LINGO_API_KEY`) | Non : le modèle est configuré côté plateforme |
| `lingo.dev` (`bunx lingo.dev@0.138.10`) | 0.138.x | traduction locale, appelle directement le modèle | Oui (BYOK `openai` + `baseUrl`) |

Détails qui coûtent du temps si on les ignore :

- La commande `run` du CLI 0.138.x passe `baseUrl` en `baseUrl` au SDK OpenAI, qui attend `baseURL` : la requête part vers `api.openai.com`. Utiliser la commande `i18n` (dépréciée mais fonctionnelle), qui, elle, honore l'URL.
- `provider.prompt` est obligatoire et doit être une chaîne ; `null` fait échouer la validation du schéma, et le CLI réécrit alors `i18n.json` sans le bloc `provider`.
- `buckets` attend un objet : `{ "json": { "include": ["lang/[locale].json"] } }` (ancien format : tableau de chemins).
- Le CLI ne sait pas extraire du code PHP/Blade : il ne traduit que ce qui existe déjà dans un fichier source. Une chaîne ajoutée avec `__('...')` dans une vue doit d'abord apparaître dans `lang/en.json`.
- L'extraction se fait par expression régulière sur `app/**/*.php` et `resources/views/**/*.blade.php` ; les clés contenant `$`, `{{` ou `}}` sont à exclure (interpolation Blade, la clé réelle change à l'exécution).
- Le CLI réécrit `i18n.json` après chaque exécution (ajout de `$schema`, normalisation du `version`) : c'est normal.

## Ajouter une langue

1. Ajouter le code dans `locale.targets` de `i18n.json` **et** dans `supported_locales` de `config/app.php`.
2. Relancer la commande : le fichier `lang/<code>.json` est créé.
3. La locale active est posée par `app/Http/Middleware/SetApplicationLocale.php` à partir du réglage applicatif.

Si le `version` de `i18n.json` casse après une exécution, remettre simplement `"locale"`, `"buckets"` et `"provider"` dans le fichier.
